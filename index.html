1. Проектирование n-tier приложений

Тема 1 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

1.1. Что такое архитектура информационной системы

Архитектура ИС — концепция, определяющая модель, структуру, выполняемые функции и взаимосвязь компонентов информационной системы.

Архитектурный паттерн — зарекомендовавшее себя решение чётко обозначенной проблемы, принятое сообществом программистов.

1.2. Какие бывают архитектуры из лекции

  • Монолитная — одно приложение/проект, внутри которого находятся необходимые классы и функции.
  • Многослойная (Layered) — приложение разделено на программные слои по ответственности. Типично: данные → бизнес-логика → представление.
  • Многоуровневая (Multi-tier / N-tier) — физическое разделение частей приложения на отдельные уровни.
  • Событийно-ориентированная (Event-driven) — компоненты взаимодействуют через события; связи менее жёсткие, возможна асинхронная работа.
  • Микроядерная (Microkernel) — есть ядро, а бизнес-функциональность распределена по плагинам.
  • Микросервисная — приложение разбито на несколько самостоятельных сервисов/приложений, каждый со своей бизнес-логикой.

1.3. Слой и уровень — не одно и то же

Слой (layer) — программная абстракция. Например, слой бизнес-логики или слой доступа к данным.

Уровень (tier) — физически отделённая часть системы. Разные уровни могут находиться на разных компьютерах/серверах и даже быть реализованы разными технологиями.

Главное: layer отвечает на вопрос «как логически разделён код?», tier — «где физически выполняется часть системы?».

1.4. Многослойная архитектура

Каждый слой выполняет свою функцию. Основной принцип — разделение ответственности.

  • Слой данных/Model — описывает данные и взаимодействует с источником.
  • Бизнес-логика — реализует основные функции приложения.
  • Представление — отвечает за ввод и вывод.

Плюсы: относительно простая разработка, поддержка и тестирование, модульность. Минусы: дополнительные переходы между слоями могут влиять на производительность; серьёзное расширение может быть сложным.

1.5. Multi-tier / N-tier

В N-tier логические части физически разделены. Типичный пример — клиент-сервер: клиентский компьютер → сервер приложения → сервер БД.

Плюсы: масштабируемость, распределение нагрузки, возможность разделить ответственность и ресурсы. Минусы: сложнее развёртывание и обслуживание; производительность зависит от сетевого взаимодействия.

1.6. Другие архитектуры

Event-driven: компоненты реагируют на события. Плюсы — масштабируемость, отзывчивость, асинхронность, гибкость. Минусы — сложнее тестирование, контроль порядка событий и согласованности данных.

Microkernel: ядро координирует плагины. Если отдельный плагин сломался, система может продолжить работу. Плюсы — расширяемость, поддержка, тестирование. Минусы — накладные расходы и риск неправильного разделения функций.

Microservices: несколько самостоятельных сервисов могут быть написаны на разных языках и масштабироваться независимо. Минусы — сложнее тестирование и возможна несогласованность данных между сервисами.

Что сказать на экзамене: дать определение архитектуры → перечислить виды → объяснить layer vs tier → описать N-tier и пример клиент-сервер → назвать плюсы/минусы.

Готовый ответ для экзамена

Архитектура информационной системы — концепция, определяющая модель, структуру, выполняемые функции и взаимосвязь её компонентов. Архитектурный паттерн — проверенное решение чётко обозначенной проблемы. В лекции рассматриваются монолитная, многослойная, многоуровневая, событийно-ориентированная, микроядерная и микросервисная архитектуры. В монолитной системе всё реализовано в одном приложении. В многослойной каждый слой выполняет свою функцию: представление отвечает за ввод-вывод, логика — за функции приложения, слой данных описывает данные и взаимодействует с источником. Это облегчает поддержку и замену источника данных, но переходы между слоями могут снижать производительность. Слой — программная абстракция, а уровень — физически отделённая часть системы. Пример многоуровневой архитектуры — клиент-сервер: клиент, сервер приложения и сервер БД. В событийной архитектуре компоненты общаются событиями; в микроядерной ядро координирует плагины; в микросервисной система состоит из независимых приложений-сервисов.

2. Проектирование слоя доступа к данным. ADO.NET

Тема 2 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

2.1. Зачем нужен DAL

DAL (Data Access Layer) — программный слой, предоставляющий упрощённый доступ к данным в постоянном хранилище: реляционной БД, файлу и т.п.

Идея: Model описывает сущности, DAL получает данные из источника и преобразует их в сущности, бизнес-логика работает с этими сущностями.

2.2. Почему не работать с файлом напрямую

Файл может быть неудобен для реального приложения из-за блокировок файловой системы. Файлы подходят для небольших объёмов данных, редких изменений и однопользовательских приложений.

2.3. Реляционная БД

Данные хранятся в таблицах. СУБД управляет доступом к данным. SQL используется для основных операций: SELECT, INSERT, UPDATE, DELETE.

2.4. ADO

ADO — низкоуровневый способ работы: программист открывает соединение с БД, отправляет SQL, получает «сырые» данные и сам выполняет нужное сопоставление типов.

Плюсы: максимальный контроль над SQL и возможностью оптимизации запросов.

Минусы: нужно знать SQL; типы данных приходится сопоставлять с типами языка программирования.

2.5. Mapping

Mapping (маппинг) — установление соответствия между данными из одного набора/структуры и соответствующими полями другой структуры. Например, строка таблицы БД превращается в объект C#.

Коротко: DAL отделяет источник данных от остального приложения. ADO даёт контроль, но много работы остаётся программисту.

Готовый ответ для экзамена

Слой доступа к данным (DAL) — программный слой, упрощающий доступ к постоянному хранилищу: файлу или базе данных. Модель описывает сущности, DAL получает данные из источника и преобразует их в объекты, а бизнес-логика работает с моделью и DAL. Для файлов характерны ограничения при совместном доступе; они подходят для небольших объёмов, редких изменений и одного пользователя. Реляционная БД хранит данные в таблицах, а SQL позволяет выполнять SELECT (чтение), INSERT (добавление), UPDATE (изменение) и DELETE (удаление). При использовании ADO.NET программист открывает соединение и отправляет SQL-запросы, а преобразование полученных данных в типы программы выполняет сам. Это даёт контроль над запросами и их оптимизацией, но требует знания SQL и ручного сопоставления типов. Mapping — установление соответствия между полями исходных данных и полями объекта.

3. Repository. Unit of Work

Тема 3 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

3.1. Repository

Repository — класс, инкапсулирующий необходимую для доступа к источнику данных логику и ориентированный на доменные объекты. Он отделяет технологию доступа к данным от модели предметной области.

Внутри может быть ADO, Dapper, EntityFramework, работа с файлом или удалённым хранилищем. Пользователь репозитория видит CRUD-операции, а детали скрыты.

CRUD: Create — создание, Read — чтение, Update — изменение, Delete — удаление.

Доменный объект обычно представляет сущность и содержит в основном свойства; он соответствует данным предметной области/таблице.

3.2. IRepository

Часто репозиторий описывают интерфейсом IRepository. Бизнес-логика зависит от абстракции, а конкретный класс реализует её. При замене технологии можно заменить реализацию репозитория, не переписывая бизнес-логику.

Плюсы: ремонтопригодность, модульность, более чистое описание объектов. Минусы: больше кода, сложности с нешаблонными запросами.

3.3. Unit of Work

Unit of Work — контейнер, управляющий несколькими репозиториями и обеспечивающий использование одного контекста данных.

В сложных вариантах он накапливает изменения из разных репозиториев и отправляет их одной транзакцией либо откатывает.

3.4. Проблемы Repository/UoW

  • репозитории могут разрастаться из-за уникальных запросов;
  • сложны запросы с объединением таблиц;
  • абстракция может скрывать полезные особенности конкретной технологии.

Особенно проблемны сложные JOIN при ручных технологиях вроде ADO/Dapper: приходится собирать результаты нескольких репозиториев.

На экзамене: определение Repository → что скрывает → IRepository → плюсы/минусы → Unit of Work → его назначение и проблемы.

Готовый ответ для экзамена

Repository — класс, инкапсулирующий логику доступа к источнику данных и ориентированный на объекты предметной области. Он скрывает конкретную технологию хранения (например, файл, ADO, Dapper или Entity Framework) и предоставляет операции CRUD: Create — создать, Read — прочитать, Update — изменить, Delete — удалить. Часто репозиторий описывается интерфейсом IRepository, а конкретная реализация может заменяться без переписывания бизнес-логики. Преимущества: модульность, сопровождаемость и отделение доступа к данным. Недостатки: дополнительный код, сложность уникальных запросов и объединений таблиц; абстракция может скрывать возможности технологии. Unit of Work — объект, управляющий несколькими репозиториями и общим контекстом данных; может накапливать изменения и сохранять их одной транзакцией либо откатывать. В лекции отмечено, что Entity Framework уже реализует идеи Repository и Unit of Work через наборы сущностей и DbContext, поэтому дополнительная обёртка нужна не всегда.

4. Dapper

Тема 4 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

Что такое Dapper

Dapper — технология автоматического сопоставления данных. Программист пишет SQL-запрос, а Dapper преобразует результат в объекты/типы C#.

То есть по сравнению с ADO часть ручной работы с mapping автоматизирована, но SQL остаётся под контролем программиста.

Установка: через NuGet.

Плюсы: высокая скорость, гибкость SQL, контроль над запросом.

Минусы: необходимо знать SQL; сложные многотабличные запросы могут быть неудобны.

ADO: SQL + много ручного mapping → Dapper: SQL + автоматический mapping → EF: более высокий уровень абстракции и ORM.
Запомнить: Dapper не убирает SQL — он прежде всего упрощает mapping результата SQL-запроса.

Готовый ответ для экзамена

Dapper — библиотека для автоматического сопоставления результата SQL-запроса с объектами C#. Программист по-прежнему пишет SQL, но не выполняет вручную всё преобразование строк результата в объекты. Библиотеку подключают через NuGet. Преимущества: гибкость SQL и высокая скорость. Недостатки: нужно знать SQL, запросы остаются ручными, а сложные объединения нескольких таблиц могут быть неудобны. Главное отличие от ADO: Dapper автоматизирует mapping. В отличие от Entity Framework, он не скрывает SQL так сильно.

5. EntityFramework

Тема 5 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

Что такое EntityFramework

EntityFramework (EF) — полноценная ORM-система (Object-Relational Mapping), которая берёт на себя mapping и позволяет работать с данными через объекты и LINQ.

Как работает

Создаётся DataContext, который сообщает ORM, какие коллекции сущностей есть в приложении. Программист работает с объектами и LINQ, а EF формирует SQL.

Изменения могут накапливаться, а SaveChanges() формирует необходимые SQL-операции и сохраняет изменения одной транзакцией.

Плюсы: абстракция от SQL, стандартные запросы, объектный стиль, удобная работа с joins.

Минусы: нестандартные запросы могут быть неудобны; из-за дополнительной абстракции производительность в некоторых случаях ниже.

CRUD

Create — добавить запись; Read — прочитать; Update — изменить; Delete — удалить.

Главная разница: ADO даёт SQL и всё делает программист; Dapper оставляет SQL, но автоматизирует mapping; EF сильнее абстрагирует программиста от SQL и работает как ORM.

Готовый ответ для экзамена

Entity Framework (EF) — ORM, то есть средство объектно-реляционного отображения: оно связывает объекты программы с данными реляционной базы. Программист работает с сущностями и запросами на C#/LINQ, а EF формирует SQL. Контекст данных описывает наборы сущностей; изменения могут накапливаться, а SaveChanges отправляет необходимые операции в базу. Преимущества: меньше ручной работы с SQL и сопоставлением данных, единый стиль запросов, удобная работа со связями и объединениями, накопление изменений. Недостатки: нестандартные запросы могут быть неудобны, а дополнительная абстракция в некоторых случаях снижает производительность. Сравнение: ADO — SQL и много ручной работы; Dapper — SQL плюс автоматический mapping; EF — более высокий уровень абстракции и работа с объектами.

6. MVC, MVP

Тема 6 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

6.1. MVC

MVC = Model–View–Controller. Подход разделяет данные/модель, представление и управление взаимодействием.

  • Model — описание доменных сущностей; может быть тонкой (только данные) или толстой (данные + бизнес-логика).
  • View — отображает данные и принимает ввод; бывает активной или пассивной.
  • Controller — реагирует на сигналы View, изменяет Model и при необходимости управляет View.

Важное правило лекции: Model не знает о View и Controller. Это позволяет разрабатывать и тестировать её независимо.

Observer в MVC

Активная Model может уведомлять зависимые объекты об изменениях через Observer/события.

6.2. MVP

MVP = Model–View–Presenter. Это вариант MVC: Model толстая, View пассивная, а Controller превращается в Presenter и управляет View.

Пассивная View сама не получает изменения модели — Presenter организует взаимодействие.

В реализации MVP слои желательно связывать через абстракции/интерфейсы. Presenter может быть отдельным исполняемым проектом, чтобы избежать циклической зависимости проектов.

Разница

MVCMVP
ControllerPresenter
View может быть активнойView пассивная
Model может быть тонкой/толстойКанонический MVP — толстая Model
На экзамене: расшифровать MVC/MVP, описать роли трёх компонентов и отдельно объяснить активную/пассивную View и Model.

Готовый ответ для экзамена

MVC означает Model–View–Controller (Модель–Представление–Контроллер). Model описывает сущности предметной области; она бывает тонкой (только данные) или толстой (данные и бизнес-логика). View отображает данные и принимает пользовательский ввод; представление бывает активным или пассивным. Controller реагирует на сигналы представления, изменяет модель и при необходимости управляет представлением. Важный принцип лекции: Model не знает о View и Controller. Активное представление само получает данные модели, пассивное получает их через контроллер. Активная модель сообщает об изменениях, пассивную модель контроллер проверяет сам. Для уведомления об изменениях используется Observer (Наблюдатель): объект сообщает подписчикам об изменении состояния. MVP — вариант MVC: Model толстая, View пассивная, Controller называется Presenter и управляет View. В MVP важно взаимодействовать через абстракции/интерфейсы.

7. MVVM

Тема 7 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

Что такое MVVM

MVVM = Model–View–ViewModel. В лекции это вариация MVC: активная тонкая Model + активная View, а Controller заменён ViewModel.

  • Model — тонкая, описывает сущности.
  • View — активная; в WPF получает данные через механизмы binding.
  • ViewModel — реагирует на сигналы View, работает с Model и предоставляет данные/действия для View.

WPF-механизмы

Data Binding связывает элементы View со свойствами объекта. DataContext задаёт контекст, где View ищет связанные свойства.

INotifyPropertyChanged позволяет сообщить View, какое свойство изменилось. Событие передаёт имя свойства, после чего View получает актуальное значение.

ObservableCollection сообщает об изменениях коллекции.

ICommand представляет действие как объект. В лекции рассматривается RelayCommand с делегатами выполнения и проверки возможности выполнения.

Важно: Command — самостоятельный паттерн, а не часть WPF. WPF лишь предоставляет удобные механизмы его использования через binding.

Сравнение

MVC: Model + View + Controller. MVP: толстая Model + пассивная View + Presenter. MVVM: тонкая Model + активная View + ViewModel.

Готовый ответ для экзамена

MVVM означает Model–View–ViewModel (Модель–Представление–Модель представления). В изложении лекции это вариант MVC с тонкой активной Model и активной View; роль контроллера выполняет ViewModel. Model описывает сущности, View показывает интерфейс, а ViewModel реагирует на действия пользователя и связывает View с Model. В WPF используются механизмы привязки данных (Data Binding): элемент интерфейса связан со свойством объекта. DataContext указывает, в каком объекте искать связанные свойства. INotifyPropertyChanged сообщает, какое свойство изменилось; ObservableCollection сообщает об изменениях коллекции. ICommand позволяет представить действие как объект; RelayCommand содержит делегаты выполнения действия и проверки, можно ли его выполнить. По лекции Command — самостоятельный паттерн, а не часть WPF.

8. Структурные паттерны. Decorator

Тема 8 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

Что такое структурные паттерны

В лекции на примерах рассматриваются паттерны, которые помогают организовать взаимодействие и структуру объектов: Decorator, Adapter, Facade, Template Method. Для билета главное — Decorator, но полезно знать назначение остальных.

Decorator

Decorator динамически наделяет объект новым функционалом и является гибкой альтернативой субклассированию при расширении функциональности.

Идея — обёртка: есть исходный объект, затем его оборачивают декоратором, который добавляет поведение. Можно последовательно оборачивать объект несколькими декораторами.

Пример лекции: напиток → декоратор сахара → декоратор молока → итоговый напиток.

Наследование не подходит, если набор добавляемых функций должен меняться во время выполнения. Декоратор позволяет динамически собирать нужную комбинацию.

Другие паттерны из лекции

Adapter преобразует интерфейс одного класса к интерфейсу другого, чтобы несовместимые классы могли работать вместе.

Facade предоставляет единый упрощённый интерфейс к сложной подсистеме.

Template Method задаёт скелет алгоритма и оставляет отдельные шаги наследникам.

Для Decorator запомнить: «динамически добавляет функциональность объекту», «обёртка», «альтернатива наследованию».

Готовый ответ для экзамена

Decorator (Декоратор) — структурный паттерн, который динамически добавляет объекту новую функциональность, оборачивая его в объект-декоратор с совместимым интерфейсом. Исходный объект сохраняет свою основную работу, а декоратор добавляет поведение и может передавать вызов дальше. Несколько декораторов можно соединять, получая разные комбинации возможностей. Это альтернатива созданию множества подклассов, когда комбинации дополнительных функций должны гибко меняться. Пример: напиток оборачивается декоратором добавления молока, а затем декоратором добавления сахара. В лекции также рассматриваются Adapter (согласует несовместимые интерфейсы), Facade (предоставляет упрощённый интерфейс к сложной подсистеме) и Template Method (задаёт общий порядок шагов алгоритма, позволяя переопределять отдельные шаги). Для билета главное подробно раскрыть Decorator.

9. Порождающие паттерны. Фабричный метод. Singleton

Тема 9 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

Порождающие паттерны

Это шаблоны, которые упрощают и контролируют создание объектов, абстрагируя систему от конкретного способа их порождения.

Фабрика и Factory Method

Простая фабрика выносит повторяющийся код выбора и создания разных типов объектов в отдельный класс.

Factory Method дополняет фабрику: позволяет создать семейство фабрик, где конкретная фабрика выбирает конкретную реализацию продукта. Пример лекции — сеть пиццерий: в разных городах один и тот же запрос создаёт разные варианты пиццы.

Singleton

Singleton (Одиночка) гарантирует, что для определённого типа будет создан только один экземпляр.

Классическая реализация из лекции: private-конструктор → static-поле/свойство с экземпляром → метод/свойство для получения экземпляра.

Плюсы: гарантия одного экземпляра; единая точка создания; удобный доступ.

Минусы: способ создания становится неочевидным; существуют обходы; исходная форма не обеспечивает корректность в многопоточных/асинхронных приложениях.

В лекции отмечено, что Singleton многие считают антипаттерном, но это не означает, что инструмент нельзя применять.

Не путать: Factory Method решает задачу создания разных реализаций; Singleton — задачу ограничения экземпляра одним объектом.

Готовый ответ для экзамена

Порождающие паттерны связаны с созданием объектов. Фабрика (простая фабрика в материалах) выносит выбор создаваемого объекта в отдельное место. Factory Method (Фабричный метод) определяет способ создания объекта через метод, позволяя конкретным реализациям выбирать, какой продукт создавать; клиентский код меньше зависит от конкретного класса. Singleton (Одиночка) гарантирует, что у класса существует единственный экземпляр, и предоставляет общую точку доступа к нему. Классическая реализация Singleton использует закрытый конструктор, статическое поле с экземпляром и метод/свойство для его получения. Плюсы: один экземпляр и единая точка доступа. Минусы, отмеченные в лекции: создание объекта становится менее очевидным; обходные пути могут позволить создать второй экземпляр; простая реализация не обеспечивает безопасность при многопоточном/асинхронном доступе. В лекции также отмечено, что Singleton нередко считают антипаттерном, хотя он бывает полезен.

10. Поведенческие паттерны. Стратегия

Тема 10 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

Поведенческие паттерны

Определяют алгоритмы и способы взаимодействия объектов, распределяя ответственность между ними.

Strategy

Стратегия определяет семейство алгоритмов, инкапсулирует их и делает взаимозаменяемыми. Алгоритмы можно изменять независимо от клиента.

Простое объяснение из лекции: замена множества IF/Switch на отдельные классы. Изменяющуюся часть алгоритма выносят в отдельную сущность, а основному классу передают нужную реализацию.

Пример: у мага разные типы заклинаний — нанести урон, вылечить, усилить или ослабить. Вместо большого switch создаётся общий тип стратегии MagicSpell и разные реализации.

Связь с SOLID

В лекции Strategy используется как способ соблюдения OCP: изменяющееся поведение выносится за пределы класса, а новые варианты добавляются новыми реализациями.

Формула ответа: семейство алгоритмов → инкапсуляция → взаимозаменяемость → независимое изменение от клиента → пример.

Готовый ответ для экзамена

Strategy (Стратегия) — поведенческий паттерн, который определяет семейство алгоритмов, инкапсулирует каждый из них и делает их взаимозаменяемыми. Алгоритм можно менять независимо от кода, который его использует. Вместо множества условий клиент использует общий интерфейс стратегии, а конкретная стратегия выполняет нужный вариант алгоритма. Пример: разные способы сортировки, расчёта скидки или оплаты можно оформить как отдельные стратегии и выбирать нужную. Паттерн связан с принципом OCP: поведение можно расширять добавлением новой реализации, не переписывая основной код, если он работает через абстракцию.

11. Принципы SOLID

Тема 11 из 11

Мой статус по теме

Отмечай «уверен» только если можешь ответить без конспекта.

Что такое SOLID

SOLID — акроним набора практик проектирования, направленных на создание гибкого и адаптивного кода.

S — Single Responsibility Principle

Принцип единственной ответственности: каждый компонент должен иметь только одну причину для изменения.

Компонент должен выполнять одну задачу или один набор тесно связанных задач. Например, вывод, работу с файлами и бизнес-логику лучше разделять.

Распространённые обязанности, которые выделяют отдельно: хранение данных, валидация, уведомления пользователя, обработка ошибок, создание объектов, форматирование, парсинг.

O — Open/Closed Principle

Принцип открытости/закрытости: сущности программы открыты для расширения, но закрыты для изменения.

Последующие изменения желательно реализовывать добавлением нового кода, а не переписыванием существующего. В лекции Strategy используется для вынесения изменяющегося поведения в отдельные реализации.

L — Liskov Substitution Principle

Принцип подстановки Лисков: вместо базового типа должна быть возможность подставить любой его подтип без изменения работы программы.

Поведение наследника не должно противоречить поведению базового класса и должно оставаться ожидаемым для кода, работающего с базовым типом.

Пример: квадрат как наследник прямоугольника может нарушать ожидаемое поведение ширины/высоты. Значит, иерархия должна строиться с учётом поведения в программе, а не только отношений предметной области.

I — Interface Segregation Principle

Принцип разделения интерфейсов: клиенты не должны вынужденно зависеть от методов, которыми не пользуются.

Проблемы «жирного» интерфейса: слишком большой интерфейс, слабо связанные компоненты, пустые методы в классах только ради поддержки интерфейса.

Решение — разделить интерфейс на несколько частей с логически связанными методами/свойствами.

D — Dependency Inversion Principle

Принцип инверсии зависимостей: модули верхнего уровня не должны напрямую зависеть от модулей нижнего уровня; оба должны зависеть от абстракций.

Абстракции определяют контракт, а не детали. Реализации/детали должны зависеть от абстракций.

Зависимость — ситуация, когда один класс ссылается на другой. Сильная зависимость усложняет тестирование, расширение и изменение.

Как связать SOLID в голове

  • S: не смешивай разные причины изменения.
  • O: добавляй новое, не ломая старое.
  • L: наследник должен нормально заменять базовый тип.
  • I: не заставляй клиента зависеть от лишнего.
  • D: завись от абстракции, а не от конкретной детали.
На экзамене по SOLID: расшифровать SOLID → назвать все 5 принципов → дать формулировку каждого → кратко объяснить смысл → привести пример/нарушение хотя бы для основных принципов.

Готовый ответ для экзамена

SOLID — пять принципов проектирования, помогающих создавать гибкий и сопровождаемый код. S — Single Responsibility Principle, принцип единственной ответственности: у класса должна быть одна основная ответственность и одна причина для изменения. O — Open/Closed Principle, принцип открытости/закрытости: программные сущности должны быть открыты для расширения, но закрыты для изменения; новое поведение предпочтительно добавлять через новые реализации/абстракции. L — Liskov Substitution Principle, принцип подстановки Барбары Лисков: объект подкласса должен заменять объект базового класса без нарушения ожидаемого поведения программы. I — Interface Segregation Principle, принцип разделения интерфейсов: клиент не должен зависеть от методов, которыми не пользуется; большие интерфейсы следует делить на логически связанные. D — Dependency Inversion Principle, принцип инверсии зависимостей: модули верхнего уровня не должны напрямую зависеть от модулей нижнего уровня; оба должны зависеть от абстракций, а детали должны зависеть от абстракций. Нужно уметь раскрыть все пять названий, объяснить каждый и привести хотя бы простой пример нарушения/решения.
